## 背景・目的

`POST /auth/login` はユーザー名を持たない単一パスワード認証であり、試行回数の制限が一切ない。リポジトリを一般公開すると認証設計とエンドポイント構成が既知になるため、本番URLが判明した場合にオンラインでのパスワード総当たりを妨げるものが Argon2 の計算コストのみになる。

同一送信元からの試行が一定回数に達したらブロックし、総当たりの成立を実用上不可能な水準まで下げる。

設計の背景・採用しなかった方式・受容する残存リスクは [docs/architecture.md 25節](../docs/architecture.md#25-管理者ログインのレート制限post-authlogin) にまとめてある。**実装前に必ず通読すること。** とくに「カウントは『照合の前』に行う — 競合の排除」は、この機能の正しさを左右する中心的な設計判断である。

## 設計の要点（実装前に理解すべきこと）

### なぜ「照合の前」に数えるのか

素朴に実装すると、次の順序になりやすい。**この順序で実装してはならない。**

```
1. ロックを取得してブロック判定 → ロックを解放
2. auth_service::try_login(...).await     ← Argon2 + DB往復で約100ms
3. 失敗なら、ロックを取得して失敗を記録
```

判定（読み取り）と加算（書き込み）が別のロック区間に分かれ、その間に約100msの `await` がある。この間カウンタは増えないため、**同一キーから同時に多数のリクエストが到着すると、そのすべてが「まだ0回」の状態で判定を通過する**。5回という上限が事実上「同時実行数」に置き換わり、総当たりを妨げられない。

正しくは、**ブロック判定と加算をひとつのロック区間の中で不可分に行い、パスワード照合より前に加算を完了させる**。数えるのは「失敗回数」ではなく「試行回数」になるが、正しいパスワードでの試行は成功時に記録ごと削除されるため、正規の管理者に対する挙動は変わらない。

### カウンタは単調増加させる

カウンタが減るのは「認証成功」と「時間経過（15分）」のときだけとする。**DBエラーで照合の成否が判定できなかった場合も、加算を取り消さない。** 取り消しを許すとDB障害中にレート制限が停止し、また取り消しが世代を区別できないため別の期間のカウンタを減らしてしまう（理由の詳細は設計書25節）。

## 実装仕様

### `src/services/login_attempt_service.rs`（新規）

現在時刻を引数で受け取る純粋なロジックとして実装する。`chrono::DateTime<chrono::Utc>` を使う（プロジェクトの既存の時刻表現に合わせる。`src/services/game_service.rs` を参照）。

- 定数: 試行の上限 `MAX_ATTEMPTS: u32 = 5`、ブロック期間 `BLOCK_DURATION_MINUTES: i64 = 15`、掃除のしきい値 `CLEANUP_THRESHOLD: usize = 1024`
- 記録の型（例: `AttemptRecord`）は「試行回数」と「最後に試行した時刻」を持つ。**フィールド名は `failures` ではなく `attempts` のように、実際に数えているもの（試行）を表す名前にすること**
- **モジュール外へ公開する関数は次の3つだけとする**。判定と加算を分離したプリミティブを公開すると、それらを個別に呼ぶ実装によって競合を再導入できてしまうため
  1. **試行を登録し、その場でブロック判定を返す関数**（例: `register_attempt`）
     - 引数: 記録のマップ、キー、現在時刻
     - 戻り値: ブロック中なら残り時間、そうでなければ「受け付けた」ことを示す値（`enum` を推奨）
     - 動作: ブロック中でなければ試行回数を1増やしてから「受け付けた」を返す。ブロック中なら**加算せずに**残り時間を返す
     - 最後の試行から15分以上経過している場合は、それ以前の回数を捨てて1回目として数え直す
  2. 成功時に記録を削除する関数（例: `record_success`）
  3. 期限切れの記録を掃除する関数（例: `cleanup`）
     - **記録件数が `CLEANUP_THRESHOLD` を超えたときだけ**走査する。しきい値以下なら即座に戻る（全件走査しない）
- 内部で使う判定・加算のヘルパーは、モジュール内に閉じる（`pub` にしない）。同一ファイル内の `#[cfg(test)] mod tests` からは引き続きアクセスできる
- **加算を取り消す関数は作らない**

### `src/main.rs`

- 型エイリアスを追加する（`StampImageCache` の定義（現在の23行目付近）に倣う）
  ```rust
  pub type LoginAttemptStore = Arc<Mutex<HashMap<String, login_attempt_service::AttemptRecord>>>;
  ```
  `StampImageCache` は `RwLock` だが、こちらは読み取り時にも必ず更新（加算）が走るため `Mutex` でよい
- `AppState` にフィールド `login_attempts: LoginAttemptStore` を追加し、`AppState::new` で空の状態を初期化する
- `handlers::auth::login` が `AppState` からこのストアを受け取れるようにする。現在 `login` ハンドラーは `State(pool): State<MySqlPool>` を取っているため、`State<AppState>` に変更してよい（`FromRef<AppState> for MySqlPool` は既にあるため、他のハンドラーへの影響はない）

### `src/handlers/auth.rs`

`login` ハンドラーの処理順を以下にする。**順序を守ること。**

1. CSRFトークンの検証（既存のまま。失敗なら `403`。**この失敗は試行回数に数えない**）
2. `X-Forwarded-For` からキーを求める（後述）
3. 現在時刻を**一度だけ**取得し、以降の判定・記録すべてでその値を使い回す
4. **ロックを取得し、その中で「掃除 → 試行の登録とブロック判定」を行い、ロックを解放する**
5. ブロック中なら**パスワード照合を行わずに** `429 Too Many Requests` を返す
   - `Retry-After` ヘッダーに残り秒数を**切り上げた**整数を設定する
   - ボディはログイン画面を再描画し、「試行回数の上限に達しました。しばらく待ってから再度お試しください」といった趣旨のメッセージを表示する（既存の `render_login` の `error_message` を活かす。ステータスコードは `429` にすること）
6. `auth_service::try_login` でパスワードを照合する
7. `Ok(true)`（成功）: 記録を削除してから、既存のセッション処理（`insert` → `cycle_id`）とリダイレクトを行う
8. `Ok(false)`（パスワード誤り）: **何も記録しない**（手順4で加算済み）。既存どおりエラーメッセージ付きでログイン画面を再描画する
9. `Err(_)`（DBエラー）: **何も記録しない**（加算したままにする）。既存どおり `500` を返す

**手順4〜5をパスワード照合より前に置くこと**が重要。ブロック中にArgon2の計算とDBアクセスを行うと、攻撃者が容易にCPUとDB接続を消費できてしまう。

クライアントIPの抽出は、テスト可能な独立した関数として実装する。

- `X-Forwarded-For` ヘッダーの**最後の行**のみを見る（同名ヘッダーが複数行に分かれて届く場合があり、プロキシは末尾に追記するため最後の行が最も信頼できる）
- その行がUTF-8として解釈できない場合、または値を取り出せない（空・カンマのみ）場合は、**それより前の行に遡らず** `unknown` を返す。前の行はクライアントが送った可能性のある値であり、遡ることは攻撃者の制御下にある値をキーに採用することを意味する
- 最後の行が取得できたら、その中でカンマ区切りの**最も右の**空でない値をトリムして返す

## 制約・注意事項

- **ロックを跨いで `await` しないこと。** 手順4のロックは `HashMap` 操作のみで完結させ、`try_login` の前に必ず解放する
- **既存のログイン成功・失敗の挙動（リダイレクト先・エラーメッセージ・`cycle_id` によるセッションIDのローテーション）を変えないこと。** 追加するのはブロック判定のみ
- ブロック中の応答は `429`。`403` や `401` にしないこと（[docs/api.md](../docs/api.md) に `429` として記載済み）
- 送信元を問わない全体（グローバル）上限は**実装しないこと**。第三者が正規の管理者を締め出せる（設計上の判断。architecture.md 25節参照）
- `std::thread::sleep` を使うテストを書かないこと。現在時刻は必ず引数で渡す
- 掃除を省略しないこと。また、しきい値による条件付き実行を省略して毎回全件走査にしないこと。どちらも設計書25節に理由がある
